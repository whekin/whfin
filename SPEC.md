# whfin — personal finance tracker (Android)

Замена ZenMoney под личные сценарии. Главный принцип: **минимум ручного труда** —
транзакции приходят сами (SMS), сверяются автоматически (выписка), категории запоминаются навсегда.

## Боли ZenMoney, которые решаем

- Ненадёжный банк-синк, постоянный рассинхрон
- Не запоминает мерчант → категория (магазин, перевод → аренда)
- Неудобный учёт долгов
- Корректировка баланса портит статистику
- UI

## Источники данных

| Источник | Роль | Статус транзакции |
|---|---|---|
| SMS банков (Credo / TBC) | оперативная проводка с provenance `SMS`; участия не требует, кроме действительно неоднозначного routing | активная операция, позже тихо сверяется выпиской |
| Excel-выписка (MYCREDO / TBC xlsx) | источник правды, сверка | `confirmed` |
| MyCredo private connector (experimental) | JSON history по явному запуску, automatic initial XLSX and reconciliation; продолжение в Android-службе | `confirmed` |
| TBC mobile connector | API history по явному запуску и карточные блокировки после XLSX или введённого владельцем остатка; продолжение в Android-службе | проведённые `confirmed`, блокировки `pending` |
| Ручной ввод / виджет | кеш, корректировки | `manual` |
| Крипто watch-адреса | EVM/Tron balances; подтверждённая история Tron USDT/USDC | balance snapshot + операции CRYPTO |

### Реконсиляция (ядро анти-рассинхрона)

При импорте выписки: матчим SMS-транзакции по **нормализованный мерчант + дата покупки**
(дата покупки есть в SMS и внутри Description выписки; дата списания на 1–2 дня позже).
Сумму матчим с допуском: FX-платежи в SMS в валюте покупки (USD/EUR/GBP), в выписке — GEL по курсу расчёта.
Выписка перезаписывает SMS-строку и обогащает (Beneficiary Name + IBAN), даже если пользователь уже
подтвердил её вручную: provenance `source=SMS` остаётся кандидатом реконсиляции до замены на
`source=STATEMENT`. Несматченные строки выписки → новые confirmed.
Для переводов между своими счетами и конвертаций используется только единственный точный кандидат
того же ledger и суммы в узком окне ±1 день: Credo может отнести движение сразу после полуночи к
предыдущему банковскому дню. Повторный импорт также чинит уже возникшую пару statement+SMS, приводя её
к тому же результату, что и успешная первичная сверка; неоднозначность никогда не разрешается молча.
Balance в каждой строке выписки → сверка цепочки баланса.
Полная Credo-выписка также сверяет количество старых statement-копий с разными остатками:
точные группы сохраняют исходные ID, категории и реальное число повторных платежей. Защищённые
связи не объединяются автоматически. Room 8 хранит хеши и подтверждённые количества строк в истории
импорта и backup, чтобы старый файл не удалял позднее подтверждённый повтор. Контракт и ограничения:
[docs/bank-evidence-reconciliation.md](docs/bank-evidence-reconciliation.md).

### Формат выписки Credo (проверено на приватных тестовых выписках)

- Лист `Account Details`: holder, period (`dd.MM.yyyy - dd.MM.yyyy` или текущий
  `dd/MM/yyyy : dd/MM/yyyy`), IBAN, currency, opening/closing balance
- Лист `Transactions`: Date, Operation (17 грузинских типов — стабильные ключи), Turnover DB/Cr, Balance, Description, Beneficiary Name/Account
- Карточные операции (`საბარათე ოპერაცია`): `გადახდა - {MERCHANT} {AMOUNT} GEL {дата покупки}`
- Переводы между своими счетами + конвертации = transfer (не расход/доход!), их ~170/год
- Комиссии (`ლარის გადარიცხვის საკომისიო`) отдельными строками сразу за родительским переводом — приклеивать

### Формат SMS Credo (проверено на приватных fixtures)

6 типов: Payment, Outgoing transfer, Incoming transfer, Transfer between accounts, Currency exchange, Rejected payment (скип).
Мусор: `CODE: NNNNNN confirms...`, хвост `want to split the bill? ...`.

Каждый Credo-кандидат получает локальный явный outcome. Raw body не хранится: Room содержит только
hash, тип, masked/parsed поля и результат. История читается отдельным `READ_SMS` действием за 90 дней,
с dry-run перед записью; неизвестная карта/неоднозначный счёт исправляются через явный mapping UI.
Если все допустимые счета на дату сообщения уже покрыты банковской историей, выбора счёта нет:
SMS остаётся свидетельством для последующей сверки, но не создаёт вторую операцию.
Для неоднозначной конвертации UI выводит вычисленные пары подходящих текущих счетов одного банка:
один тап сразу проводит обе ноги. Demand/term deposits и legacy savings-ledgers в конвертации не
участвуют; отдельные сохранённые «сценарии» не создаются.

**Ловушки:**
- Два формата даты: Payment `dd/MM/yyyy HH:mm:ss` (24ч), переводы `M/d/yyyy h:mm:ss AM/PM`
- FX-платежи: сумма в валюте покупки, Balance в GEL
- Мерчант: `spar>Tbilisi`, `NIKORA TRADE JSC>DIDGORI` → нормализация: lowercase, отрезать `>город страна`, trim + таблица алиасов
- `Card N ****0001 / ****0002` → маппинг карта→счёт (две синтетические карты, один GEL-счёт)
- В SMS перевода нет получателя — обогащается выпиской

### SMS TBC и расширение Credo

Общая модель сообщений отделена от банковских парсеров. Отправитель определяет банк;
карты с одинаковыми последними цифрами, выбор счёта и сверка выпиской разделены по банкам.
TBC: покупки с маской карты, возвраты, пополнения, внешние переводы и коммунальные платежи;
недостаточные для проводки шаблоны остаются в диагностике. Доступный остаток TBC не становится
проведённым балансом. Credo получил однострочные платежи/отмены, старые даты/подписи,
часть транслитерации и точное чтение знака суммы. Полный аудит оставшихся вариантов:
[docs/bank-message-formats.md](docs/bank-message-formats.md). Push требует отдельного подключения.

## Модель данных (Room, суммы в minor units / Long)

- **Account**: name, type (`BANK | CASH | SAVINGS | CRYPTO | PERSON`), currency, iban?, isArchived; card masks отдельной таблицей.
  Валютные ledgers одного `(groupId, iban)` образуют один UI-контейнер: пользовательское имя и
  роль средств и банковский продукт меняются для них атомарно, но баланс и история всегда остаются
  раздельными по валюте. Роль средств (`AVAILABLE | RESERVE`) отвечает только за пользовательское
  деление доступных денег и резерва. Банковский продукт (`CURRENT_ACCOUNT | DEMAND_DEPOSIT |
  TERM_DEPOSIT`) описывает договор с банком и не определяет роль средств. Поэтому депозит до
  востребования может быть доступным, а обычный счёт или наличные — резервом.
- **Transaction**: accountId, amountMinor (signed), currency, origAmountMinor?/origCurrency? (FX),
  occurredAt (дата покупки), postedAt? (дата списания), merchantId?, counterpartyName/Iban?,
  categoryId?, note, status (`PENDING | CONFIRMED | MANUAL`), source (`SMS | BANK_HOLD | STATEMENT | MANUAL | ADJUSTMENT | CRYPTO`),
  transferPeerId? (парная транзакция перевода), balanceAfterMinor?, externalKey (дедуп)
- **Category**: дерево 2 уровня, name, icon, color, kind (`EXPENSE | INCOME`), isSystem; системная **Unaccounted**
- **Merchant**: normalizedKey, displayName, categoryId (память навсегда); **MerchantAlias**: pattern → merchant

## Ключевые фичи

1. **Категоризация-память**: раз присвоил мерчанту категорию — она запоминается; то же работает для отправителей (`EXAMPLE EMPLOYER` → Salary) и получателей (`EXAMPLE LANDLORD` → Rent). В Настройках есть единый экран «Умные категории»: покрытие считается по расходным операциям, неизвестные мерчанты сгруппированы и отсортированы по числу операций, а один выбор исправляет всю ещё не размеченную историю мерчанта и становится правилом для следующих SMS/Credo-импортов. Автоматически применяются только объяснимые локальные правила с высокой уверенностью; сомнительное остаётся в явной очереди проверки.
2. **Корректировка баланса** — транзакция первого класса: разница → системная категория Unaccounted, видна в статистике отдельно, ничего не ломает
3. **Виджет** (Glance) — добавить расход не открывая приложение: сумма + категория + счёт; кеш-шаблоны одним тапом
4. **Общий итог в одной валюте**: остатки всех счетов, включая крипту, сводятся по курсам НБГ
   (фиат) и CoinGecko→USD→GEL (крипта); тап по итогу переключает GEL/USD/RUB. Пересчёт — только
   чтение: история не переоценивается, волатильные активы не входят в доходы/расходы.
   Детали: [docs/exchange-rates.md](docs/exchange-rates.md)
5. **Статистика по месяцам**: свайп по месяцам, расходы → доход и результат → вклады категорий в отличие от среднего по записям, тренды; мультивалютность через пересчёт в базовую
6. **Накопления**: любой ledger можно считать резервом независимо от банковского продукта.
   План накопления объявляет желаемый месячный темп в одной валюте, но не создаёт fake ledger-операций и ничего
   не требует подтверждать. Его изменение действует с явного календарного месяца и не переписывает прошлое.
   Фактический темп — чистое управляемое движение Available↔Reserve: пополнение резерва помогает выполнить план,
   возврат в Available или расход из резерва его уменьшает, Reserve→Reserve не влияет. Проценты, внешний доход, opening anchors
   и balance adjustments меняют баланс резерва, но не выдаются за привычку откладывать. Желаемый баланс и срок опциональны;
   достижение цели ничего автоматически не закрывает и не переводит. Внутренние переводы не являются расходом.
   Экран открывается по Reserve в Accounts; темп и баланс имеют отдельные графики за год/всё время,
   валюты не смешиваются. Контракт и ограничения: [docs/savings.md](docs/savings.md).
   Прогноз показывает будущий рост по месячному плану даже без цели: горизонты 1/2/5 лет и выбор
   месяца ползунком. Календарь в live-редакторе сразу показывает ожидаемую сумму к выбранной дате
   и необходимый темп; изменение суммы пересчитывает дату достижения цели. Факт рисуется сплошной,
   прогноз — пунктиром. Сценарий не обещает доходность: равные взносы, первый через месяц от сегодня,
   без предполагаемых процентов, снятий и курсов; в ledger до/после сохранения плана ничего не пишется.
   Home не предлагает «пополнить резерв»: перевод остаётся действием банка. В Savings можно открыть
   установленный официальный MyCredo/TBC только для соответствующего резервного счёта; это обычный
   launch intent без суммы и реквизитов, а Demo workspace никогда не ведёт в реальный банк.
   Тот же обычный запуск доступен из предупреждения низкого баланса карты на Home — только для
   соответствующей банковской группы и установленного consumer app, без записи перевода.
7. **Долги**: отдельные `DebtCase` + журнал `DebtEvent`, а не PERSON-счета. Долг бывает связан с
   движением по реальному счёту или создан без движения. Возврат может прийти другой суммой, валютой
   и на другой счёт; закрытие обязательства — явное действие, не результат сравнения банковских сумм.
8. **Доходы**: зарплата (плавающая дата — ок, календарный месяц; опция «финансовый месяц» позже), подработки, продажи
9. **Точка входа зарплаты**: объявляется счёт получения, сумма, одна ориентировочная дата и правило
   выходных — обязательной границы «не позже» нет, иначе приложение назовёт опоздавшей выплату внутри
   её же нормального разброса. Прошедшая дата означает «ждём», а не следующий месяц. Приход на счёт
   доказательством не является: владелец подтверждает выплату один раз, дальше узнаётся отправитель,
   а сумма опознанием не служит никогда. Частичные выплаты складываются.
10. **Перевод между своими счетами** доступен на любой обычной операции: связать с уже загруженной
    строкой другого своего счёта или записать недостающую сторону вручную (наличные). Сторон может
    быть больше двух, обе стороны сохраняют свою сумму, валюту, дату и provenance, связка обратима, а
    разница между сторонами остаётся разницей — комиссией она становится, только когда так сказано.
    Посредник — необязательная информация, а не источник дохода.

## UI/UX

- Jetpack Compose, Material 3, светлая/тёмная/системная тема (DataStore)
- Локализация EN + RU с первого дня
- Просто и красиво — дизайн приоритет
- Навбар без разделительной линии; месячная сводка выделяет факт и прогноз. Отфильтрованная история
  имеет свой заголовок. В настройках выбор темы показывает миниатюры, поиск в заголовке непрерывно
  раскрывается и сворачивается жестом; длинные пояснения не добавляются.
- Первый нетронутый запуск показывает один Welcome choice: Personal setup или изолированный Demo
  workspace, без permission-карусели. Personal setup строится вокруг поддерживаемого банка и его
  реальных каналов; statement-файл остаётся запасным ручным путём. Настройка охватывает Credo/TBC,
  независимые SMS/push, счета и остатки, категории, доходы, накопления и долги, оформление и защиту.
  Каждый этап опционален, формы возвращаются в мастер после успешного сохранения, текущий этап переживает перезапуск.
  После первого успешного входа Credo/TBC мастер сам переходит к Bank SMS; история продолжает загружаться
  в приложении. На следующих шагах видны общий для обоих банков статус и действия, если нужны
  подтверждение остатков или повтор. Категории, найденные в личных расходах, предлагают только по
  ещё не размеченным операциям; необязательные наборы можно выбрать и добавить вместе.
  В шаге Bank SMS одно действие включает мониторинг для всех поддерживаемых банков; индивидуальные
  исключения остаются в Подключениях. Старые SMS проверяются отдельно перед импортом.
  Шаги показывают сохранённые факты; итог сверяет остатки по валютам с датированными банковскими данными.
  Совпадение с датированным банковским остатком не требует дополнительной галочки; просмотренное
  расхождение остаётся явно названным. Автосозданный пустой Cash не создаёт фиктивную задачу сверки,
  а действие завершения ждёт первого полного чтения локальных остатков.
  Подробности раскрываются по запросу. Ожидание банка отделено от выбора счёта или категории.
  Начальный синк по-прежнему читает всю историю. Контракт: docs/first-run-demo-and-bank-sms.md.
- SMS monitoring, routing и import — разные состояния. Parsed SMS без выбранного ledger показывается
  в Feed как приглушённая Unrouted operation, не влияет на balance/statistics и открывает contextual
  resolver. Routed SMS сразу является обычной операцией; `SMS` показывается как её источник, а не как
  pending/review-задача. Пользовательская поверхность называется Bank SMS, а parser diagnostics остаётся деталями.
- Demo workspace не является глобальным switch: вход находится вторичной строкой Settings, активный
  workspace явно обозначен по всему приложению, а новый Demo visit начинается с канонического fixture.
- Основная карта — один явно выбранный payment instrument во всём workspace. GEL-ledger, связанный с
  основной физической картой, помогает держать запас на продукты; пока основная карта не выбрана,
  действует совместимый fallback на все физические карты. Если основной выбрана virtual-карта,
  physical-card предупреждение намеренно молчит. Home сразу под итогом
  месяца предупреждает о риске следующей оплаты; ниже 150 GEL сумма и явная подпись переходят в
  warning-состояние, ниже 100 GEL — в error-состояние. При первом переходе
  ниже 100 GEL отправляется уведомление; повтор разрешается только после восстановления до 100 GEL.
  Виртуальные карты и ledgers других валют в это правило не входят.

- Оценка «хватит ли до выплаты» на Home отделена от месячного прогноза Statistics: уже совершённые
  крупные разовые покупки влияют через текущий остаток, но не повторяются в будущем дневном темпе.
  Доказанные ежемесячные платежи исключаются из повседневного среднего и учитываются отдельно по
  ожидаемым датам до крайнего срока выплаты, включая следующий месяц. Объявление даты не является
  равновероятным окном: первое число — обычная выплата, второе — редкий край. Основной прогноз идёт
  до обычной даты; суббота/воскресенье сдвигает ориентир на понедельник, а край показывается отдельным
  сценарием задержки. Уже увиденная выплата переносит прогноз на следующий месяц. Расчёт раскрывается
  до платежей и итоговой суммы; короткая история и неоценённые расходы не дают ложной уверенности.
  Это оценка по истории, не подтверждённое расписание. Контракт: `docs/home-screen.md`.

## Безопасность и переносимость данных

- До первого реального использования модель намеренно сведена к одной чистой Room DB v1 без legacy-
  миграций. После фиксации первого пользовательского релиза каждое изменение схемы обязано получить
  явную data-preserving migration; destructive fallback на пользовательском устройстве запрещён.
- Основной переносимый backup — версионированный JSON через SAF, спроектированный для round-trip
  restore. Raw SMS, OTP, app-lock secrets, банковские пароли/токены и Keystore keys не экспортируются.
- Незашифрованный JSON считается чувствительным файлом и требует предупреждения. Позже допускается
  зашифрованный контейнер `.whfin-backup` поверх того же логического формата.
- Системный Android backup — дополнительный канал восстановления: явный allowlist только для Room
  database и non-secret UI/widget preferences; cloud backup разрешён лишь при encryption capability,
  device-to-device transfer использует тот же scope. Банковские tokens/secrets должны храниться отдельно.
- Публичный demo mode использует отдельную `whfin-demo.db` с полностью синтетическим fixture и никогда
  не восстанавливает поверх `whfin.db`. Demo DB и локальные флаги demo/developer исключены из Android
  backup; входящие SMS, виджет и quick entry остаются явно привязаны к пользовательской базе.
- App Lock использует системный `BiometricPrompt`: strong biometric или PIN/pattern/password устройства,
  с настраиваемым timeout и сокрытием содержимого в recent apps. Виджет не раскрывает баланс на
  заблокированном устройстве без явного opt-in.
- Для личной dogfood-сборки разрешён отдельный foreground-коннектор к текущему веб-протоколу MyCredo:
  он только скачивает XLSX,
  не выполняет платежей и не обещает стабильность. Login и пароль можно не сохранять; при явном opt-in
  и активной App Lock они хранятся только device-local одним AES-256-GCM ciphertext единственного формата с
  non-exportable Android Keystore key, без plaintext-дубликата username и вне Android/JSON backup.
  OTP и session tokens существуют только в памяти текущего входа. Connector принимает только ожидаемый
  Credo HTTPS host без redirect; это read-only поверхность WHFIN, а не банковское ограничение credential.
  Успешный полный foreground-прогон, включая прогон без новых строк, сохраняет только время последней
  сверки; после обновления приложения baseline берётся из последнего сохранённого `CREDO_SYNC` import,
  поэтому напоминание не возникает заново сразу после установки версии с этой функцией. Через 7 дней
  Home показывает одну спокойную строку `Сверить Credo`: сколько дней прошло и
  сколько активных SMS-операций ещё ждут подтверждения выпиской. Это не пользовательская очередь
  подтверждения; тап — явный запрос `sync latest`: сохранённый вход → OTP → загрузка свежих операций
  продолжаются без второй кнопки. Back возвращает туда, откуда Credo был открыт. Первый синк сам
  догружает всю доступную историю; отдельное действие остаётся для продолжения неполного прогона.
  Если часть выписок не скачалась из-за временной сетевой/5xx ошибки, следующий foreground retry
  запрашивает только неудавшиеся ledgers: уже импортированные не запрашиваются повторно. Список
  продолжения переживает перезапуск/обновление приложения device-local и очищается после успешной
  догрузки; незавершённая первая синхронизация старой версии восстанавливается по account-level
  `CREDO_SYNC` imports только при отсутствии маркера завершённого прогона. Ручной targeted retry
  делает ровно один download-запрос на каждый неудавшийся ledger, без повторного внутреннего backoff.
  При сохранённом входе обычный экран показывает только профиль MyCredo и действие синхронизации —
  поля login/password и управление credential доступны только при первичной настройке или из Settings.
  Контракт и границы: [docs/credo-private-sync.md](docs/credo-private-sync.md).
- История выписок хранит происхождение загрузки (`FILE | CREDO_SYNC | CREDO_API | TBC_SYNC | USER_OPENING`) отдельно от банковского
  StatementSource. Ручные и MyCredo-загрузки показываются вместе. Безопасно удалить можно только no-op
  повтор; результативная загрузка остаётся audit record, пока не реализован обратимый transaction-level provenance.
- Восстановление исключает одновременную банковскую/крипто/файловую загрузку, сохраняет safety copy
  атомарно с заменой базы и сбрасывает старое состояние экранов. Контракт: [docs/backup-restore-safety.md](docs/backup-restore-safety.md).
- Подробный порядок реализации и критерии готовности: [docs/roadmap.md](docs/roadmap.md).

Подключения 0.3.29: постоянная кнопка синхронизации на Главной, недельная подсказка, прямой API Credo
и создание банковского счёта через подключение по умолчанию. [Контракт](docs/bank-api-sync.md).

Первый банковский синк в 0.3.30 загружает всю доступную историю. Нулевой остаток не является
условием остановки. Credo определяет раннюю границу по API и проходит годовые XLSX; TBC читает
страницы до конца. Позднее обновляются свежие операции с перекрытием. [Контракт](docs/bank-api-sync.md).

Подключения 0.3.31: сохранённый вход TBC показывается отдельно от формы пароля и сохраняется
сразу после подтверждения банка. Выбор «Запомнить вход» и объяснение expiry переживают перезапуск.
Этот этап сохранял только сессию; следующий этап ниже распространяет правило сохранения пароля и на TBC. [Контракт и дизайн](docs/bank-connection-design.md).

В 0.3.32 «Запомнить вход» — единое правило банков: зашифрованные логин и пароль под блокировкой
WHFIN, действующая сессия как быстрый путь, при её истечении — повторный вход без ручного ввода.
Одноразовые коды не сохраняются; TBC получил подстановку через SMS/Android SMS Consent.
[Контракт](docs/bank-authentication.md). Поиск Настроек прокручивается вместе со списком и превращается
в иконку справа в topbar; нажатие возвращает поле и фокус без отдельного collapsing-scroll поведения.

### Исправление ошибочного остатка при подключении банка

В Account activity можно исправить USER_OPENING через меню счёта: владелец задаёт, каким должен
быть баланс по уже записанным операциям. Меняется только начальная основа расчёта; сегодняшний
расход/доход не создаётся. Подтверждённый выпиской остаток так не редактируется. Изменение записей
во время открытой формы требует нового просмотра перед сохранением. Название счёта и IBAN
показываются без дублей; тап по сумме открывает ввод фактического баланса, редактирование реквизитов — компактное действие у названия.

### Получатель пользы при создании расхода

В новом расходе, включая наличные, «Для кого» выбирается до сохранения. По умолчанию весь расход
на себя; можно выбрать существующего человека или ввести нового. Вся сумма — GIFT, половина —
SHARED с остатком PERSONAL; долг не создаётся. Половина считается от окончательной суммы,
нечётная минимальная единица остаётся на себе. «Кому заплатили» — отдельный контрагент.
Новый человек, расход и доли сохраняются атомарно одним действием; отменённая форма не создаёт
человека. Выбор получателя не переносится на доход, перевод или долг. Существующие сложные
разбивки редактируются через детали операции.

В быстром расходе из виджета доступен тот же выбор «Для кого». Строка стоит под категориями;
полный выбор человека — отдельный шаг, после которого сохраняются сумма калькулятора, категория,
порядок подсказок и прокрутка формы. Ввод работает со встроенным keypad и системной клавиатурой.
Widget продолжает писать в userDb, даже при открытом Demo. Новый наличный счёт при fallback,
новый человек, операция и доли создаются атомарно; ошибка оставляет черновик в форме, повторный
тап во время записи не создаёт вторую операцию.

### Настройки и подключения

Корень содержит пять разделов: Подключения, Учёт, Приложение, Данные и безопасность,
О приложении. Общий поиск находит конечные настройки во всех разделах; возврат со страницы
банка восстанавливает запрос. По умолчанию поле скрыто за иконкой справа в topbar. Иконка открывает поле с клавиатурой;
протягивание корневого списка вниз тоже открывает поле с фокусом и клавиатурой. Поле остаётся частью одного scroller. Контракт: docs/settings-navigation.md.

В Подключениях каждый банк представлен одной строкой с состоянием. Страница банка объединяет
обновление истории, каналы получения операций, валютные счета, сохранённый вход и диагностику.
SMS включаются отдельно для каждого банка; системное разрешение общее. Вход и API-синхронизация
не включают мониторинг SMS. Существующий opt-in Credo/TBC сохраняется при обновлении.

### Push TBC и журнал примеров

Отдельный opt-in в Настройки → Подключения → TBC подключает NotificationListenerService только для TBC Bank.
Два известных формата карточных покупок — расходы; неизвестные, входящие и противоречивые
форматы ждут разбора. Общая сверка с SMS/API и выпиской не создаёт вторую покупку для одного
совпавшего события. Сырой доступный текст push и результат обработки сохраняются локально в
зашифрованном журнале (30 дней, до 300 записей, ограничение размера). Коды входа не сохраняются.
Журнал не входит в backup и не отправляется автоматически. Пример можно просмотреть, выгрузить
через системный выбор файла и обработать повторно. Очистка журнала не удаляет операции.
Контракт и ограничения: docs/tbc-push.md.

### Редактирование баланса и карточка операции — 0.3.39

Тап по балансу обычного валютного счёта открывает фактическую сумму и разницу до сохранения.
Ноль и отрицательные суммы допустимы, дробные minor units и переполнение отвергаются.
Новая операция во время редактирования делает форму устаревшей: требуется открыть её заново.
После сохранения доступна быстрая отмена; позже ручную корректировку можно удалить через меню
её карточки. Удаление убирает только этот delta и пересчитывает баланс по оставшимся операциям.
Начальные остатки и audit-записи сверки не удаляются этим действием. USER_OPENING по-прежнему
исправляется отдельно; быстрая отмена относится к обычной корректировке текущего баланса.

Категория — заметный редактируемый блок до статуса. Выбор имеет поиск; назначение и отмена выбора
возвращают карточку операции. Мерчант и запоминание его категории сохраняют прежние правила.

### Предварительные покупки TBC — 0.3.42

Foreground Sync записывает блокировки карточных покупок как BANK_HOLD/PENDING с подписью
«Ожидает списания». Они учитываются в расходах и остатке, не требуют ручного подтверждения.
Push, блокировка и окончательное списание связываются с одной операцией, с сохранением категории
и ID. Неоднозначное совпадение или изменение суммы с долями/долгом требует разбора.
Исчезновение блокировки не считается автоматической отменой. Durable aliases входят в backup;
Room 6→7 добавляет отдельную таблицу связей без изменения существующих операций.
Подробный контракт и границы: docs/tbc-pending.md.

### Остатки SMS Credo — 0.3.43

Неподписанный Balance в переводе между своими счетами присваивается только той стороне,
которая единственная совпадает с расчётом от предыдущего банковского остатка. Неоднозначный
остаток не создаёт опору для следующих SMS. В конвертациях остаток помогает выбрать валютный
счёт, но оба счёта должны определяться однозначно; конвертации между разными IBAN допустимы.
Старые ошибочные привязки остатков доступны в Проверке данных как предпросмотр с явным
подтверждением. Меняются только поля balanceAfterMinor, не суммы/счета/существование операций.
Фонового исправления истории нет. Контракт: docs/credo-sms-balance-review.md.

### Повторные выписки Credo — 0.3.44

Изменившийся остаток после покупки сам по себе не создаёт новую операцию. Точное однозначное
совпадение полного описания, обеих дат, суммы и реквизитов обновляет существующую строку,
сохраняя её ID, категорию и API-связь. Точные ключи имеют приоритет; настоящие повторные покупки
не сливаются. Неоднозначность останавливает импорт счёта. Уже записанные пары автоматически
не объединяются. Контракт: docs/credo-statement-revisions.md.

### Явное объединение дублей Credo — 0.3.45

Проверка данных показывает кандидатов из повторных выписок и предлагает выбрать одну пару,
если это была одна покупка. До подтверждения записи не меняются. Сохраняются исходный ID и
категория; банковский остаток и ключ берутся из новой копии. Лишняя копия сохраняется как merged,
но больше не учитывается в расходах; корректировочная транзакция не создаётся. Есть немедленная
отмена до изменений в учёте в пределах текущего экрана. Доли, долги, переводы, конфликт категорий,
API-идентичности и платежи 1 GEL не объединяются этим действием. Устаревший предпросмотр требует
повторного чтения. Контракт: docs/credo-statement-revisions.md.

В 0.3.46 предпросмотр дублей поддерживает чекбоксы и «Выбрать все / Снять выбор». Одна кнопка
объединяет выбранные пары; до нажатия видны их число и суммарное изменение по валютам.
Проверка и запись всей группы атомарны, немедленная отмена восстанавливает всю группу.

### Полнота истории и сверка Credo — 0.3.48

После синка полнота каждого ранее импортированного счёта независимо сверяется с ранней границей
API. Если она уже покрыта, «Fetch older history» скрывается без повторного экспорта; неизвестная
граница не считается завершённой историей. Обычные конвертации с общим временем проходят через
API, fallback XLSX остаётся для групп карточных конвертаций. Свои переводы Credo различаются также
по реквизитам встречного счёта при единственном совпадении. Неоднозначный API-план атомарно
отклоняется и допускает сверку текущей выпиской. Остаточная ошибка называется ошибкой сопоставления,
а не нечитаемой выпиской. Контракт docs/bank-api-sync.md.

### Прогресс и повторные запросы Credo — 0.3.49

Экран отдельно показывает сопоставление карт и проверку глубины банковской истории, с текущим
счётом этой проверки. Полученная ранняя граница переиспользуется при немедленной догрузке того же
синка. Подтверждённые привязки карт кэшируются только внутри одной транзакции обработки SMS;
отрицательные результаты не кэшируются. Правила денежных записей не меняются.

### Сверка нескольких источников — 0.3.50

Связь SMS с операцией переживает проведение и повторное чтение сообщения. Credo сверяет полную
группу карточных сообщений с одной суммарной банковской строкой при точном совпадении суммы,
карты, валюты, мерчанта и дня. Переводы используют тип сообщения и однозначные реквизиты;
явно будущая напечатанная дата допускает дополнительную проверку по дате получения SMS.
Настоящие повторные переводы и мелкие покупки сохраняют число операций. Ключ с остатком не
позволяет переставить мерчантов у покупок одинаковой суммы. После файлового sync Credo показывает
расхождение остатка на конец выписки отдельно от успешной загрузки. Денежная корректировка
не создаётся. Правила, ограничения и проверки: docs/bank-evidence-reconciliation.md.

### Синхронизация без ожидания на экране — 0.3.52

После подтверждения банка и начала загрузки истории возвращаемся на Home. Иконка синхронизации
показывает активную работу; по нажатию видны этап, номер счёта и результат каждого банка. Открытие
результата не запускает новый вход. Credo и TBC продолжают явный синк при сворачивании приложения
и уничтожении Activity через dataSync foreground service. Коды и сессии не передаются в Intent
или уведомление. После гибели процесса показывается прерывание, повтор — явным действием владельца.
Контракт, ограничения Android и проверки: docs/bank-background-sync.md.
